Описан ли визуальный паттерн: каждая swimlane-строка содержит все три колонки, даже если в некоторых нет задач? [Completeness, Spec §FR-001] — **Да. Data-model: визуальное представление показывает матрицу с пустыми Droppable-областями. Research §3: «Каждый swimlane содержит все три колонки статуса, даже если в некоторых нет задач»**.
- [x] CHK002 Указано ли в плане, где и как отображается количество задач в swimlane (FR-012)? Определено ли, считается ли общее количество или отдельно по колонкам? [Completeness, Spec §FR-012] — **Да. Plan (Количество задач): «В заголовке swimlane отображается общее количество задач (суммарно по всем колонкам)». Data-model: «Количество задач — Общее количество задач в swimlane (суммарно по всем колонкам)»**.
- [x] CHK003 Описано ли в плане, как именно swimlane «Без категории» отображается всегда первым (FR-013)? Учтено ли, что это правило применяется и когда «Без категории» — единственный swimlane? - [x] CHK004 Определено ли в плане поведение при drag-and-drop задачи в колонку, которая не содержит ячейки в целевом swimlane (пустая ячейка)? [Gap, Spec §FR-010] — **Да. - [x] CHK005 Указано ли в плане, как GET /api/tasks/swimlanes обрабатывает параметр date, если на указанную дату нет задач? [Completeness, Spec §FR-009] — **Да. - [x] CHK006 Определено ли в плане, как фильтрация assignees и swimlanes комбинируется в GET /api/tasks? Уточнено ли, что это логическое И, а не ИЛИ? [Completeness, Contracts §GET /api/tasks] — **Да. - [x] CHK007 Описано ли в плане, как bulk-операции (bulk delete, bulk move, move-incomplete-to-tomorrow) из спецификации 003 взаимодействуют с полем swimlane? [Gap, Dependencies] — **Да. Research §10: «Поле swimlane сохраняется при bulk-операциях... Swimlane НЕ очищается и NOT переназначается автоматически»**. Task T046 покрывает тестирование.

Research §4: «Значение — JSON-массив нормализованных (lowercase) ключей swimlane». Data-model: «Сворачивание — UI-состояние, хранится в localStorage по нормализованному ключу»**.

Data-model: «ключ = «без категории» (lowercase), отображаемое имя = «Без категории»». Contracts: «Если swimlaneKey === «без категории» → отправить swimlane: null»**.

## Согласованность требований (Requirement Consistency)

- [x] CHK014 Согласовано ли правило «первого вхождения» (FR-011) между backend и frontend? На backend GetSwimlanesAsync группирует через `.GroupBy(t => t.Swimlane!.ToLower())`, а на frontend группировка через `toLocaleLowerCase()` — нет ли расхождения в алгоритмах нормализации? [Consistency, Research §2] — **Да. Research §2 явно отклоняет toLocaleLowerCase() и предписывает .toLowerCase() на обеих сторонах: «на frontend — использовать ту же нормализацию .toLowerCase() (не toLocaleLowerCase()), чтобы гарантировать совпадение ключей»**.
- [x] CHK015 Согласовано ли хранение свёрнутого состояния с регистронезависимостью swimlane? Если пользователь свернул «Фронтенд», а ключ хранится как «фронтенд» (lowercase), будет ли сворачивание работать при переоткрытии, если backend вернёт «Фронтенд»? [Consistency, Research §2 + §4] — **Да. Все ключи нормализуются через normalizeSwimlaneKey(). localStorage хранит Set<string> нормализованных ключей. Поиск через isCollapsed() использует тот же normalizeSwimlaneKey(). Поэтому «Фронтенд» и «фронтенд» совпадут**.
- [x] CHK016 Согласовано ли правило FR-009 (swimlane без задач не отображаются) с поведением при drag-and-drop? Если пользователь перетаскивает последнюю задачу из swimlane, должен ли swimlane исчезнуть немедленно или остаться пустым до перерисовки? [Consistency, Spec §FR-009 + §FR-010] — **Да. Plan: «optimistic update: задача мгновенно перемещается, исходный swimlane исчезает. При ошибке API — откат (rollback), swimlane появляется снова»**.
- [x] CHK017 Согласовано ли поведение droppableId `{swimlane}:{status}` с регистронезависимостью? Если ключ swimlane — «без категории» (lowercase), а backend возвращает «Без категории», как парсинг droppableId разрешает это расхождение? [Consistency, Research §3 + §2] — **Да. droppableId всегда использует normalizeSwimlaneKey(). Backend возвращает displayName («Без категории»), но на frontend ключ нормализуется для droppableId. Парсинг droppableId всегда получает lowercase-ключ**.
- [x] CHK018 Согласованы ли правила валидации swimlane между CreateTaskCommand (max 100, null-нормализация) и UpdateTaskCommand? Идентична ли обработка пробельных строк и null? [Consistency, Data-model §Правила валидации] — **Да. Data-model: «Пробельные строки: string.IsNullOrWhiteSpace(swimlane) → null как на backend, так и на frontend (trim + empty → null)». Обе команды используют одинаковые правила**.

## Качество критериев приёмки (Acceptance Criteria Quality)

- [x] CHK019 Можно ли объективно проверить сценарий приёмки US-1.3: «swimlane протягивается через все колонки, и задачи размещаются в соответствующих колонках внутри этой swimlane»? Что означает «размещаются» — сортировка по order, визуальное расположение, и то, и другое? [Measurability, Spec §US-1] — **Да. Plan уточняет: «задачи внутри каждой колонки swimlane упорядочены по полю order, аналогично текущему поведению доски без swimlane»**.
- [x] CHK020 Можно ли объективно проверить US-2.3: «состояние сворачивания сохраняется и swimlane остаются свёрнутыми» после обновления страницы? Определено ли, какие именно swimlane остаются свёрнутыми — по оригинальному имени или по ключу? [Measurability, Spec §US-2] — **Да. Plan: «Ключи в localStorage — нормализованные (lowercase)». Тестовый критерий: «после обновления страницы (F5) свёрнутые swimlane остаются свёрнутыми, развёрнутые — развёрнутыми»**.
- [x] CHK021 Можно ли объективно проверить US-3.2: «автоматически создаётся новый swimlane с указанным названием»? Является ли «автоматически» достаточным критерием или нужно уточнить — без перезагрузки, без дополнительных действий, мгновенно? [Measurability, Spec §US-3] — **Да. Plan: «без перезагрузки страницы, без дополнительных действий пользователя, мгновенно через optimistic update. Новый swimlane появляется на доске сразу после сохранения задачи с новым значением swimlane»**.
- [x] CHK022 Можно ли объективно проверить US-4.1: «поле swimlane задачи автоматически обновляется на "Бэкенд", а задача остаётся в той же колонке»? Определено ли, что «автоматически» означает — без модального окна подтверждения, без перезагрузки? [Measurability, Spec §US-4] — **Да. Plan: «без модального окна подтверждения, без перезагрузки страницы, мгновенно через optimistic update. Drag-and-drop обновляет поле swimlane за один API-вызов»**.

## Покрытие граничных случаев (Edge Case Coverage)

- [x] CHK029 Определено ли в плане поведение при создании swimlane с именем, отличающимся только регистром от существующего (например, «Фронтенд» и «фронтенд»)? Соответствует ли это спецификации (FR-011 — одна и та же группа)? [Edge Case, Spec §FR-011] — **Да. Research §2: .ToLower() на backend, .toLowerCase() на frontend. Spec: «Регистронезависимы: одна и та же группа. Отображается вариант, введённый первым»**.
- [x] CHK030 Определено ли поведение при очень длинном названии swimlane (более 100 символов)? Указано ли, что происходит — обрезка, ошибка валидации, молчаливое ограничение? [Edge Case, Spec §Граничные случаи] — **Да. Frontend: maxlength на input. Backend: 400 Bad Request с сообщением «Swimlane must be at most 100 characters long». Research §11**.
- [x] CHK031 Определено ли поведение при вводе swimlane, состоящего только из пробелов? Нормализуется ли в null, как указано в data-model, и согласовано ли это со спецификацией? [Edge Case, Data-model §Правила валидации] — **Да. string.IsNullOrWhiteSpace(swimlane) → null на backend, trim() + empty check → null на frontend. Data-model, research §11**.
- [x] CHK032 Определено ли поведение при drag-and-drop в свёрнутый swimlane? Можно ли перетащить задачу в свёрнутую группу, и если да — что происходит визуально? [Edge Case, Spec §US-2] — **Да. Plan: «Свёрнутый swimlane принимает перетаскиваемую задачу. Задача обновляется через API, но swimlane не разворачивается автоматически — пользователь видит изменение счётчика задач в заголовке»**.
- [x] CHK033 Определено ли, что происходит с localStorage-состоянием свёрнутых swimlane при удалении swimlane (последняя задача ушла)? Остаётся ли «фантомная» запись в localStorage? [Edge Case, Research §4] — **Да. Research §4: «Запись остаётся в localStorage, но не вызывает проблем: несуществующий ключ не найдёт соответствующей группы и будет проигнорирован. Если пользователь заново создаёт swimlane с тем же именем — старая запись активирует свёрнутое состояние, что является ожидаемым поведением»**.
- [x] CHK034 Определено ли поведение при пустом swimlane на доске (все задачи данного swimlane находятся в одной колонке, а в других — пусто)? Отображается ли пустая горизонтальная полоса во всех колонках, как указано в граничных случаях спецификации? [Edge Case, Spec §Граничные случаи] — **Да. Data-model: «Каждый swimlane содержит все три колонки статуса, даже если в некоторых нет задач (пустая ячейка остаётся Droppable-областью)»**.
- [x] CHK035 Определено ли поведение при переименовании swimlane у одной задачи, когда другие задачи остаются с прежним значением? Соответствует ли это спецификации (FR-011 — «переименование влияет только на одну задачу»)? [Edge Case, Spec §Граничные случаи] — **Да. Research §1 (CHK041): «Переименование swimlane у одной задачи НЕ влияет на другие задачи с тем же значением»**. Спецификация: «Что произойдёт, если переименовать значение swimlane у одной задачи? → Переименование влияет только на одну задачу, остальные задачи сохраняют прежнее значение».
