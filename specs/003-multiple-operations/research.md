# Исследование: Массовые операции над задачами

**Функция**: 003-multiple-operations | **Дата**: 2026-05-23

## Обзор

Исследованы технические решения для реализации массовых операций над задачами. Основная часть инфраструктуры уже существует в кодовой базе: выделение задач (checkbox), BulkDeleteCommand, BulkMoveCommand, BulkActionsPanel. Требуется добавить только операцию «Перенести на завтра» и устранить несоответствия между спецификацией и текущей реализацией.

## Решение 1: Операция «Перенести на завтра» — серверная vs клиентская логика

**Контекст**: Спецификация требует кнопку, которая переносит все невыполненные задачи на завтра. Два подхода: (1) фильтровать задачи на клиенте и вызывать существующий bulk-move, (2) создать выделенный серверный эндпоинт.

**Решение**: Создать выделенный серверный эндпоинт `POST /api/tasks/bulk/move-incomplete-to-tomorrow`.

**Обоснование**:
- Серверный подход гарантирует атомарность — все задачи обновляются в одной транзакции
- Клиентский подход потребовал бы загрузки всех задач со всех дат (сейчас API возвращает задачи только по одной дате)
- Сервер может использовать прямые SQL-запросы для эффективности (`UPDATE tasks SET date = tomorrow WHERE status != Done`)
- Возвращает количество перенесённых задач для UI-отклика

**Альтернативы рассмотрены**:
- *Клиентский bulk-move*: Потребует загрузки задач со всех дат, затем фильтрации и отправки IDs. Нарушает текущую модель загрузки данных (по дате). Отклонён.
- *Обычный PUT по каждой задаче*: N запросов вместо одного. Отклонён по причинам производительности и атомарности.

## Решение 2: Место размещения кнопки «Перенести на завтра»

**Контекст**: Спецификация говорит «кнопка доступна всегда, а не только при просмотре определённого дня». Где разместить?

**Решение**: Разместить кнопку в Header.tsx (рядом с навигацией по датам), а не в BulkActionsPanel.

**Обоснование**:
- Кнопка действует на все невыполненные задачи, а не только на выделенные — она не является операцией над выделением
- BulkActionsPanel появляется только при выделении задач — противоречит требованию «доступна всегда»
- Header — естественное место для глобальных действий над дневным контекстом
- Кнопка визуально отделена от операций над выделением, что снижает когнитивную нагрузку

**Альтернативы рассмотрены**:
- *В BulkActionsPanel*: Кнопка была бы скрыта, когда нет выделения — нарушает требование «доступна всегда». Отклонена.
- *Отдельная плавающая панель*: Избыточно для одной кнопки. Отклонена.

## Решение 3: Удаление window.confirm из BulkActionsPanel

**Контекст**: Спецификация требует «Без диалоговых окон и подтверждений». Текущая реализация BulkActionsPanel использует `window.confirm()` для удаления.

**Решение**: Удалить `window.confirm()` из `handleBulkDelete` в BulkActionsPanel.

**Обоснование**:
- Прямое требование спецификации (FR-005, допущения)
- Согласованность UX — «Перенести на завтра» тоже без подтверждения, удаление должно быть таким же
- Массовое удаление — не деструктивная операция безвозвратно (задачи можно пересоздать)

**Альтернативы рассмотрены**:
- *Оставить подтверждение только для удаления*: Нарушает единообразие UX. Отклонена.
- *Undo-механизм*: Выходит за рамки спецификации (явно указано отсутствие отката). Отклонена.

## Решение 4: Запрос всех невыполненных задач для переноса на завтра

**Контекст**: Операция «Перенести на завтра» переносит все задачи со status ≠ Done, независимо от их текущей даты. Как получить их IDs?

**Решение**: Серверный эндпоинт сам находит невыполненные задачи. Frontend отправляет `POST /api/tasks/bulk/move-incomplete-to-tomorrow` без параметров.

**Обоснование**:
- Frontend загружает задачи только по текущей дате — не имеет доступа к задачам на других датах
- Сервер имеет прямой доступ к БД и может выполнить `WHERE Status != Done`
- Простой API: нет необходимости передавать IDs задач
- Возвращает `{ moved: number, targetDate: DateTime }` для обратной связи в UI

**Альтернативы рассмотрены**:
- *Frontend передаёт IDs*: Требует загрузки всех задач со всех дат — неэффективно и текущий API этого не поддерживает. Отклонено.

## Решение 5: Обновление UI после «Перенести на завтра»

**Контекст**: После массового переноса задач на завтра, UI должен отразить изменения. Какие задачи исчезнут из текущего дня?

**Решение**: После получения ответа от сервера, перезагрузить список задач текущего дня (`loadTasks(selectedDate)`).

**Обоснование**:
- Простейший и самый надёжный подход — сервер источник истины
- Перенесённые задачи исчезнут из текущего дня (если текущий день — сегодня) или останутся (если дата ≠ завтра)
- Согласуется с существующим паттерном в `bulkMove()` — после перемещения задачи удаляются из локального стейта и список перезагружается

**Альтернативы рассмотрены**:
- *Оптимистичное обновление*: Сложнее отследить, какие именно задачи были перенесены (сервер может вернуть список IDs). Отклонено в пользу простоты.

## Решение 6: Репозиторий — новый метод

**Контекст**: Нужен метод для получения и обновления всех невыполненных задач.

**Решение**: Добавить метод `MoveIncompleteToTomorrowAsync(DateTime tomorrow, CancellationToken)` в `ITaskRepository`, реализованный через EF Core с `ExecuteUpdateAsync` для эффективного массового обновления.

**Обоснование**:
- EF Core 7+ поддерживает `ExecuteUpdateAsync` для массовых обновлений без загрузки сущностей
- Эффективнее, чем загрузка всех задач в память и их поочерёдное сохранение
- Альтернативно можно использовать сырой SQL через `dbContext.Database.ExecuteSqlRaw`, но `ExecuteUpdateAsync` — типобезопасный идиоматичный способ

**Альтернативы рассмотрены**:
- *Загрузка + итеративное сохранение*: Существующий паттерн в BulkDelete/BulkMove. Менее эффективен, но проще. При ~100 задач разница минимальна. Выбран `ExecuteUpdateAsync` для нового метода, но паттерн итерации оставлен без изменений для существующих команд.
