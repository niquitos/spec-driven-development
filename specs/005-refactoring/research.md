# Исследование: Рефакторинг — исправление потери данных и повышение качества

**Дата**: 2026-05-28 | **Спецификация**: [spec.md](./spec.md)

## R1: Корневая причина потери свимлейна при перетаскивании

### Решение

Метод `moveTask()` в `taskStore.ts` отправляет PUT-запрос без поля `swimlane`. Бэкенд при PUT-обновлении перезаписывает все поля, и отсутствующий `swimlane` становится `null`.

### Обоснование

Анализ кода подтверждает: в `moveTask()` (строки 315-322) вызов `taskApi.updateTask()` не включает `swimlane`. Это не опечатка — это системная проблема модели PUT, где клиент обязан отправлять все поля. PATCH-модель решает это на уровне архитектуры.

### Альтернативы рассмотрены

1. **Добавить swimlane в moveTask** — быстрый фикс, но не решает корневую проблему (другие поля тоже могут быть забыты). Риск регрессии высок.
2. **Переключить PUT на PATCH** — выбрано. Решает корневую причину и делает систему устойчивой к будущим ошибкам.
3. **Оставить PUT и добавить fallback-логику** — усложняет фронтенд, не устраняет проблему системно.

## R2: PATCH vs PUT — архитектурный подход

### Решение

Добавить новый PATCH-эндпоинт `PATCH /api/tasks/{id}` для частичного обновления. Сохранить существующий PUT для формы редактирования (где все поля доступны). Фронтенд использует PATCH для перетаскивания (`moveTask`) и PUT для формы (`EditTaskModal`).

### Обоснование

Семантика JSON Merge Patch (RFC 7396): отсутствующее поле = не изменять, `null` = очистить. Это стандартный подход, хорошо понятный разработчикам и поддерживаемый ASP.NET Core из коробки (через `JsonPatchDocument` или ручной merge). PUT сохраняется для обратной совместимости — форма редактирования отправляет все поля.

### Альтернативы рассмотрены

1. **Только PATCH, удалить PUT** — нарушает обратную совместимость для существующих клиентов.
2. **Модифицировать PUT-хэндлер на merge** — нарушает семантику HTTP PUT (должен быть idempotent и полная замена).
3. **Выбранный вариант** — PATCH + PUT — наилучший баланс: новые операции используют PATCH, форма продолжает использовать PUT.

## R3: Реализация PATCH на бэкенде

### Решение

Создать `PatchTaskCommand` record с nullable-полями и `PatchTaskCommandHandler`, который загружает существующую задачу и обновляет только переданные поля. Добавить `PATCH /api/tasks/{id}` в `TasksController`.

### Обоснование

Следует существующему CQRS-паттерну проекта (Command + Handler + DI через Scrutor). Nullable-поля в command позволяют различать «не передано» (null) и «очистить» (пустая строка для строк, специальная обработка). Это проще, чем `JsonPatchDocument`, и лучше интегрируется с существующей архитектурой.

### Альтернативы рассмотрены

1. **JsonPatchDocument (RFC 6902)** — стандартный ASP.NET Core подход, но избыточен для простой сущности с ~8 полями. Требует `application/json-patch+json` content type, усложняет фронтенд.
2. **Newtonsoft.Json.Merge** — ещё одна зависимость без реальной необходимости.
3. **Выбранный вариант** — Nullable command fields — простейший подход, следующий CQRS-паттерну проекта.

## R4: Исправление SwimlaneCombobox — синхронизация props

### Решение

Добавить `useEffect` в `SwimlaneCombobox` для синхронизации `inputValue` с `value` prop при его изменении.

### Обоснование

Это стандартный React-паттерн для синхронизации локального состояния с props. `AssigneeCombobox` имеет аналогичную проблему и будет исправлена тем же паттерном.

### Альтернативы рассмотрены

1. **Контролируемый компонент** — убрать локальный `useState` и управлять состоянием извне. Изменяет API компонента, может сломать существующие использования.
2. **Выбранный вариант** — `useEffect` для синхронизации — минимальное изменение, не ломает API.

## R5: Обработка сетевых ошибок при перетаскивании

### Решение

Реализовать optimistic update с rollback: обновить UI немедленно, при ошибке — вернуть задачу на исходную позицию и показать уведомление.

### Обоснование

Текущая реализация уже использует optimistic update в `moveTask` (строки 298-310), но не обрабатывает ошибку. Добавление rollback в блок `catch` — минимальное изменение с максимальным UX-эффектом.

### Альтернативы рассмотрены

1. **Pessimistic update** — блокировать UI до подтверждения сервера. Плохой UX для drag-and-drop.
2. **Retry-механизм** — усложняет фронтенд, требует очередь запросов.
3. **Выбранный вариант** — Optimistic + rollback — стандартный паттерн для drag-and-drop, используется в Trello, Jira и др.
