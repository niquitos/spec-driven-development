# Спецификация функции: Рефакторинг — исправление потери данных и повышение качества

**Ветка функции**: `feature/005-refactoring`

**Создано**: 2026-05-28

**Статус**: Черновик

**Ввод**: Описание пользователя: "Внесение изменений в проект становится сложным. Особенно в части фронтенда. Постоянно возникают новые баги. Причина - недостаточное тестовое покрытие + запутанный код. Уже долгое время не может починиться баг с пропаданием Свимлейнов у задач. При массовом перемещении, перезагрузке страницы или еще при разных действиях на бекенд отсылаются обновления, которые обновляют задачи так, что у них пропадают свимлейны. У нас put модель обновления, это значит все поля должны быть на месте, их всегда нужно помнить и не забывать их отправлять на бекенд. Если это сложно, то можно перейти на patch модель обновления, где только переданные поля будут участвовать в обновлении. Еще одна проблема - при открытии формы создания/обновления свимлейны не проставляются автоматически в инпут. Собери текущие проблемы проекта, предложи решения."

## Пользовательские сценарии и тестирование *(обязательно)*

### Пользовательская история 1 - Сохранение данных задачи при любых операциях (Приоритет: P1)

Пользователь перетаскивает задачу между колонками (столбцами статуса) внутри одного свимлейна. После перетаскивания и перезагрузки страницы задача остаётся в том же свимлейне, в котором была до перемещения. Все поля задачи (название, описание, дата, исполнитель, свимлейн, порядок) сохраняются корректно, ни одно поле не теряется.

**Почему этот приоритет**: Это критический баг — пользователи теряют данные при рутинных операциях. Каждый перетаскивание задачи между колонками стирает свимлейн, делая канбан-доску непригодной для использования. Это блокирует основную ценность продукта.

**Независимый тест**: Можно полностью протестировать перетаскивание задачи между колонками и проверить, что свимлейн сохраняется. Это приносит ценность само по себе — пользователи смогут пользоваться доской без потери данных.

**Сценарии приёмки**:

1. **Дано** задача в свимлейне «Фронтенд» со статусом «Новая», **Когда** пользователь перетаскивает задачу в колонку «В работе» (в том же свимлейне), **Тогда** после перезагрузки страницы задача остаётся в свимлейне «Фронтенд» со статусом «В работе»
2. **Дано** задача с исполнителем «Анна» в свимлейне «Бэкенд», **Когда** пользователь перетаскивает задачу в другую колонку, **Тогда** после перезагрузки все поля задачи сохраняются: название, описание, исполнитель, свимлейн, дата, порядок
3. **Дано** задача в свимлейне «Дизайн» со статусом «Новая», **Когда** пользователь перетаскивает задачу в другой свимлейн, **Тогда** задача корректно отображается в новом свимлейне с обновлённым статусом, а старый свимлейн не теряется при промежуточных обновлениях
4. **Дано** задача без свимлейна (категория «без категории»), **Когда** пользователь перетаскивает её в другую колонку, **Тогда** задача остаётся без свимлейна, а остальные поля сохраняются

---

### Пользовательская история 2 - Автоматическое заполнение свимлейна в форме (Приоритет: P1)

Пользователь нажимает кнопку создания задачи из определённого свимлейна. Открывается форма, в которой поле «Свимлейн» автоматически заполнено названием текущего свимлейна. При редактировании задачи поле «Свимлейн» отображает текущее значение задачи и позволяет его изменить.

**Почему этот приоритет**: Это второй критический баг — свимлейны не проставляются в форме автоматически, что делает работу с доской неудобной и приводит к ошибкам. Пользователь нажимает «создать задачу» из конкретного свимлейна не просто так — он ожидает, что задача будет принадлежать этому свимлейну.

**Независимый тест**: Можно протестировать открытие формы создания задачи из свимлейна и формы редактирования задачи — в обоих случаях поле свимлейна должно отображать корректное значение.

**Сценарии приёмки**:

1. **Дано** пользователь находится в свимлейне «Фронтенд», **Когда** нажимает кнопку создания задачи, **Тогда** форма открывается с предзаполненным полем «Свимлейн» = «Фронтенд»
2. **Дано** задача в свимлейне «Бэкенд», **Когда** пользователь открывает форму редактирования задачи, **Тогда** поле «Свимлейн» отображает «Бэкенд»
3. **Дано** пользователь создаёт задачу из свимлейна «Дизайн», **Когда** отправляет форму, **Тогда** задача создаётся в свимлейне «Дизайн» без дополнительных действий
4. **Дано** задача без свимлейна (категория «без категории»), **Когда** пользователь открывает форму редактирования, **Тогда** поле «Свимлейн» отображает пустое значение

---

### Пользовательская история 3 - Частичное обновление задачи без потери данных (Приоритет: P2)

Пользователь изменяет один атрибут задачи (например, только статус или только исполнителя). Система обновляет только переданный атрибут, оставляя все остальные поля без изменений. Даже если при обновлении забыто какое-то поле, оно не теряется.

**Почему этот приоритет**: Это архитектурное улучшение, устраняющее корневую причину потери данных. Переход от модели «полная замена» к модели «частичное обновление» гарантирует, что ошибки в клиентском коде не могут привести к потере данных.

**Независимый тест**: Можно протестировать отправку обновления с одним полем и убедиться, что остальные поля не изменяются.

**Сценарии приёмки**:

1. **Дано** задача со всеми заполненными полями, **Когда** отправляется PATCH-запрос только со статусом, **Тогда** только статус изменяется, все остальные поля сохраняют прежние значения
2. **Дано** задача со свимлейном «Фронтенд», **Когда** отправляется PATCH-запрос только с порядком (order), **Тогда** свимлейн «Фронтенд» сохраняется без изменений
3. **Дано** задача с исполнителем «Анна», **Когда** отправляется PATCH-запрос с пустым полем «Исполнитель» (очистка исполнителя), **Тогда** исполнитель удаляется, а все остальные поля остаются прежними

---

### Пользовательская история 4 - Защита от регрессии через тесты (Приоритет: P3)

Разработчик вносит изменения в код задачи или свимлейна. Перед слиянием запускаются автоматические тесты, которые проверяют, что базовые операции с задачами не приводят к потере данных. Тесты покрывают ключевые сценарии: создание, обновление, перемещение, удаление задач.

**Почему этот приоритет**: Тесты — это профилактическая мера, которая предотвращает повторное появление багов. Без тестов любое изменение в коде может снова сломать сохранение данных, и это обнаружится только вручную.

**Независимый тест**: Можно создать набор тестов и убедиться, что они ловят известные баги (например, потерю свимлейна при перемещении).

**Сценарии приёмки**:

1. **Дано** существующий набор тестов, **Когда** разработчик вносит изменение, которое приводит к потере данных при обновлении, **Тогда** хотя бы один тест падает, указывая на проблему
2. **Дано** тестовый набор для фронтенда, **Когда** выполняется перетаскивание задачи между колонками, **Тогда** тест проверяет, что отправляемый запрос содержит все обязательные поля задачи
3. **Дано** интеграционный тест, **Когда** отправляется частичное обновление задачи, **Тогда** система корректно обновляет только переданные поля

---

### Граничные случаи

- Одновременное обновление одной задачи из двух вкладок решается стратегией «последний выиграл» — это приемлемо для текущей версии
- Отправка обновления с полем, содержащим только пробелы: строка из пробелов нормализуется в null (очистка поля) — и в PUT, и в PATCH режимах
- Обновление удалённой задачи: PATCH и PUT возвращают 404 Not Found
- При перетаскивании задачи с временно недоступной сетью: задача возвращается на исходную позицию, пользователь видит уведомление об ошибке
- Массовое перемещение задач, если одна из них уже удалена: уже удалённые задачи пропускаются, остальные перемещаются корректно
- PATCH-запрос с пустым телом ({}): задача не изменяется, возвращается 200 OK
- PATCH-запрос с недопустимым значением enum (status): возвращается 400 Bad Request

## Требования *(обязательно)*

### Функциональные требования

- **FR-001**: Система ДОЛЖНА сохранять все поля задачи (название, описание, дата, статус, порядок, исполнитель, свимлейн) при любом обновлении, включая перетаскивание между колонками и свимлейнами
- **FR-002**: Система ДОЛЖНА автоматически заполнять поле «Свимлейн» в форме создания задачи названием свимлейна, из которого вызвана форма
- **FR-003**: Система ДОЛЖНА отображать текущее значение свимлейна в форме редактирования задачи при каждом открытии формы
- **FR-004**: Система ДОЛЖНА поддерживать два режима обновления задачи: PUT (полная замена, используется при сохранении формы редактирования, где доступны все поля) и PATCH (частичное обновление, используется при перетаскивании и других операциях, где изменяется только часть полей); в PATCH-режиме отсутствующие поля не изменяются
- **FR-005**: В PATCH-режиме система ДОЛЖНА различать «поле не передано» (оставить без изменений) и «поле передано как null/пустое» (очистить); в PUT-режиме все поля передаются полностью; пробельные строки для полей «Свимлейн», «Исполнитель» и «Описание» нормализуются в null
- **FR-006**: Система ДОЛЖНА обрабатывать пробельные символы в поле «Свимлейн» — нормализовать строки, состоящие только из пробелов, в пустое значение (в PUT и PATCH режимах)
- **FR-007**: Система ДОЛЖНА корректно обрабатывать массовые операции (массовое перемещение, массовое удаление) без потери данных у задач, не участвующих в операции
- **FR-008**: Система ДОЛЖНА иметь автоматические тесты, покрывающие создание, обновление, перемещение и удаление задач, включая сохранение всех полей при частичном обновлении
- **FR-009**: При сетевой ошибке во время перетаскивания задачи система ДОЛЖНА вернуть задачу на исходную позицию и показать пользователю уведомление об ошибке
- **FR-010**: При PATCH-запросе с пустым телом ({}) система ДОЛЖНА вернуть ответ 200 OK без изменений в задаче
- **FR-011**: При PATCH-запросе для несуществующей задачи система ДОЛЖНА вернуть ответ 404 Not Found
- **FR-012**: При PATCH-запросе, изменяющем статус или порядок задачи, система ДОЛЖНА пересчитать порядок других задач в целевой колонке (аналогично PUT-режиму)
- **FR-013**: Валидация PATCH-запроса: если переданы поле «Название» — обязательно, max 200 символов; «Описание» — max 2000; «Исполнитель» — max 100; «Свимлейн» — max 100; недопустимые значения статуса отклоняются

### Ключевые сущности

- **Задача**: Основная сущность доски. Атрибуты: название, описание, дата, статус, порядок, исполнитель, свимлейн. Свимлейн — необязательный строковый атрибут задачи, группирующий задачи по горизонтальным рядам.
- **Свимлейн**: Виртуальная сущность, определяемая уникальными значениями поля «Свимлейн» задач на доске. Не является отдельной сущностью в хранилище — это группировка задач по значению одноимённого поля.
- **Обновление задачи**: Операция изменения атрибутов задачи. Два режима: PUT (полная замена, форма редактирования) — все поля передаются, отсутствующие поля обнуляются; PATCH (частичное обновление, перетаскивание и др.) — только переданные поля обновляются, отсутствующие остаются без изменений. В PATCH-режиме null означает «очистить поле», отсутствие поля — «не изменять».

## Критерии успеха *(обязательно)*

### Измеримые результаты

- **SC-001**: При перетаскивании задачи между колонками (внутри свимлейна и между свимлейнами) и последующей перезагрузке страницы все поля задачи сохраняются без потерь — проверяется ручным тестированием: перетаскивание → перезагрузка → все поля на месте
- **SC-002**: При открытии формы создания задачи из свимлейна (включая «без категории») поле «Свимлейн» предзаполнено корректным значением — проверяется для каждого свимлейна на доске
- **SC-003**: При открытии формы редактирования задачи (включая задачу без свимлейна) поле «Свимлейн» отображает текущее значение задачи — проверяется редактирование задачи с и без свимлейна
- **SC-004**: При PATCH-запросе с одним полем остальные поля задачи остаются без изменений — проверяется автоматическим тестом: PATCH {status: "InProgress"} → свимлейн, исполнитель, описание сохраняются
- **SC-005**: Регрессионные тесты покрывают критические сценарии: (1) перетаскивание задачи между колонками с сохранением свимлейна, (2) PATCH-обновление с частичными полями, (3) синхронизация SwimlaneCombobox с props, (4) откат при сетевой ошибке, (5) PATCH с пустым телом, (6) PATCH с несуществующим id
- **SC-006**: При сетевой ошибке во время перетаскивания задача возвращается на исходную позицию, а пользователь видит уведомление об ошибке — проверяется имитацией сетевой ошибки

## Уточнения

### Сессия 2026-05-28

- Q: Модель обновления задачи — как реализовать частичное обновление? → A: Новый PATCH-эндпоинт `/api/tasks/{id}` — только переданные поля обновляются, отсутствующие поля не изменяются
- Q: Как различать «очистить поле» и «не изменять» в PATCH? → A: PUT используется при работе с формой обновления (все поля доступны), PATCH — для частичных обновлений (перетаскивание, изменение статуса). В PATCH: поле отсутствует = не изменять, поле = null = очистить
- Q: Поведение при сетевой ошибке во время перетаскивания? → A: Откатить перетаскивание на исходную позицию и показать уведомление об ошибке
- Q: Как обрабатывать PATCH-запрос с пустым телом ({})? → A: Вернуть 200 OK, задача не изменяется
- Q: Должен ли FR-009 (откат при ошибке) распространяться на форму редактирования? → A: Нет, только на перетаскивание (PATCH). Форма редактирования имеет собственную обработку ошибок

## Допущения

- Существующая модель данных задач (поля: название, описание, дата, статус, порядок, исполнитель, свимлейн) остаётся без изменений — не добавляются новые сущности
- Частичное обновление реализуется через новый PATCH-эндпоинт; существующий PUT-эндпоинт может быть сохранён для обратной совместимости или удалён по решению при планировании
- Массовые операции (перемещение, удаление) остаются без изменений, если они уже работают корректно
- Пользователи работают с актуальной версией браузера с поддержкой современных веб-стандартов
- Одновременные обновления одной задачи из разных вкладок решаются стратегией «последний выиграл» — это приемлемо для текущей версии
- Существующие серверные тесты (модульные и интеграционные) остаются актуальными и расширяются, а не переписываются
